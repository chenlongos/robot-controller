# 整合机器人控制程序设计方案总览

## 一、架构设计概述

### 1.1 问题分析

根据需求，需要整合三个不同的机器人控制程序：

| 机器人 | 底盘类型 | 机械臂 | 摄像头 |
|--------|----------|--------|--------|
| aka00 | 双主动轮（差速） | 三关节 | USB摄像头 |
| aka01b | 四主动轮（麦轮或差速） | 六关节 | 深度摄像头 |
| Desktop-Wanderer | 三主动轮 | 六关节 | USB摄像头 |

三者的共性是"捡球放桶"的核心业务逻辑。

### 1.2 设计目标

1. **统一架构**：支持多种硬件配置的统一框架
2. **抽象隔离**：通过分层抽象隔离硬件差异
3. **配置驱动**：通过配置文件选择外设类型
4. **模块解耦**：控制单个模块复杂度

## 二、四层架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                    应用层 (Application Layer)                │
│   main.py (主控制循环)  | robot.py (机器人类, 状态机)           │
├─────────────────────────────────────────────────────────────┤
│                    控制层 (Control Layer)                    │
│  base_controller.py | arm_controller.py | vision_module.py  │
├─────────────────────────────────────────────────────────────┤
│                  抽象层 (Abstraction Layer)                  │
│     Base抽象基类 | Camera抽象基类 | Arm抽象基类                 │
├─────────────────────────────────────────────────────────────┤
│                    硬件层 (Hardware Layer)                   │
│                 Arm | Base | USB/Depth Camera               │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 层职责定义

| 层级 | 职责 | 关键模块 |
|------|------|----------|
| 应用层 | 业务逻辑编排、机器人管理 | 主循环、机器人创建、策略调度 |
| 控制层 | 运动控制算法、视觉处理 | 移动控制器、机械臂控制器、YOLO推理 |
| 抽象层 | 硬件抽象接口、设备工厂 | Base/Camera/Arm抽象基类、工厂模式 |
| 硬件层 | 具体硬件实现 | 机械臂驱动、摄像头驱动、电机驱动 |

## 四、 程序的用法

### 4.1 配置切换示例

通过修改 `config/common.yaml` 中的 `ROBOT_ID` 字段即可切换机器人类型：

```yaml
# 使用 LeKiwi
ROBOT_ID: "aka01b"
```

### 4.2 启动命令

```bash
# 启动主程序
python -m src.main
```

### 4.3 配置管理策略

- **环境变量**：通过环境变量指定 `ROBOT_ID` 来选择不同的机器人配置
- **配置版本控制**：所有配置文件纳入版本控制系统
- **配置备份**：定期备份配置文件，防止意外丢失

## 五、设计优势

### 5.1 灵活性提升

| 特性 | 说明 |
|------|------|
| **硬件无关性** | 系统不再绑定特定机器人型号，任何底盘、机械臂、摄像头的组合都能支持 |
| **配置驱动** | 通过修改配置文件即可适配新硬件，无需修改核心代码 |
| **易于扩展** | 添加新的硬件类型只需实现对应的驱动类和工厂方法 |

### 5.2 维护性改善

| 特性 | 说明 |
|------|------|
| **模块化设计** | 各硬件驱动相互独立，便于单独测试和维护 |
| **配置集中管理** | 硬件参数统一在配置文件中管理，避免硬编码 |
| **降低耦合** | 主程序通过接口与硬件交互，减少直接依赖 |

### 5.3 可复用性增强

| 特性 | 说明 |
|------|------|
| **通用组件** | 底盘、机械臂等驱动可被多个项目复用 |
| **标准化接口** | 统一的硬件接口定义，便于集成第三方硬件 |
| **配置模板** | 可为常见硬件组合创建配置模板 |

### 5.4 架构优势总结

| 特性 | 说明 |
|------|------|
| **可扩展性** | 新增机器人类型只需实现抽象基类 |
| **可维护性** | 硬件差异隔离，业务逻辑统一 |
| **灵活性** | 通过配置文件动态切换硬件配置 |
| **可测试性** | 抽象接口便于单元测试和模拟测试 |
| **代码复用** | 核心业务逻辑（捡球放桶）完全复用 |

### 5.5 预期效果

1. 三个机器人程序整合到单一仓库
2. 配置文件驱动硬件选择
3. 模块职责清晰，复杂度可控
4. 新增机器人类型的开发成本显著降低

### 5.6 后续优化方向

| 方向 | 说明 |
|------|------|
| **动态配置加载** | 支持运行时动态加载配置，无需重启系统 |
| **配置验证** | 添加配置文件格式验证，实现参数范围检查 |
| **运动自适应** | 运动过程中自动微调自身动作，以提升抓取准确度和运动速度 |
| **硬件抽象层优化** | 完善硬件接口定义，增加硬件状态监控 |
